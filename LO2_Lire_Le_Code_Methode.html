Pourquoi apprendre à lire le code ?

Quand on débute, on pense que programmer c'est écrire. En réalité, un développeur passe 70 % de son temps à lire du code — le sien ou celui des autres. Savoir lire un code efficacement est une compétence technique au même titre que savoir en écrire.

Lire un code, ce n'est pas le lire ligne par ligne comme un roman. C'est :

  • Repérer la structure (combien de classes ? de fonctions ?).
  • Identifier les entités en jeu (objets, variables, événements).
  • Suivre le flux : qui appelle qui, dans quel ordre.
  • Dresser la carte des relations entre les éléments.
  • Nommer les paradigmes présents et leur répartition.
Objectif de cette activité : à la fin, tu seras capable de prendre n'importe quel code source et d'en produire une fiche de lecture complète en moins de 15 minutes — ce qui est exactement ce que demandent les critères M2 et D2 du BTEC.

Chaque étape est détaillée ci-dessous avec un exemple guidé, une grille à remplir et un mini-exercice.

1

Vue d'ensemble — quelle est la structure ?

🎯 Objectif : avant de lire quoi que ce soit, compter. Combien de classes, de fonctions, de gestionnaires d'événements ? Cela donne une première idée du paradigme dominant.

Comment faire :

  1. Compter les class / struct → indice POO.
  2. Compter les fonctions libres (non rattachées à une classe) → indice procédural.
  3. Repérer les addEventListener, onClick, addActionListener… → indice événementiel.
  4. Repérer le point d'entrée (main, gestionnaire racine, etc.).

Exemple guidé

14 boutonPlus.addActionListener(e -> {
15     Calculatrice c = new Calculatrice();
16     c.ajouter(5);
17     afficher(c.getTotal());
18 });

2

Identifier les entités en jeu

🎯 Objectif : lister tout ce qui « existe » dans le code — objets, variables, fonctions, événements. Chaque entité a un nom, un rôle et un type.

Comment faire : surligner mentalement (ou physiquement) chaque entité et remplir un tableau à 4 colonnes : nom, type/catégorie, rôle, où elle vit.

3

Suivre le flux d'exécution

🎯 Objectif : reconstituer l'ordre dans lequel les choses se passent, depuis le point d'entrée. Ce n'est pas toujours l'ordre des lignes !

Comment faire : partir du point d'entrée et numéroter les étapes. Pour un code événementiel, commencer au moment du déclenchement (le clic).

4

Cartographier les relations

🎯 Objectif : dessiner qui appelle qui et qui contient qui. C'est l'étape la plus importante : elle transforme un mur de lignes en un schéma lisible.

Il y a 4 types de relations à repérer :

RelationSymboleSignification
Appel→A appelle la fonction B
Contenance◆—A contient un objet de type B
Événement⚡→L'utilisateur déclenche une action
Déclaration:A déclare la variable de type B

Cartographie du code Calculatrice

Utilisateur ⚡→ boutonPlus ── gestionnaire(e →)
                                │
                                ├─ crée ◆— c : Calculatrice
                                ├─ appelle → c.ajouter(5)
                                └─ appelle → c.getTotal()

c : Calculatrice ◆— total : int
                                ├─ expose → ajouter(int) : void
                                └─ expose → getTotal() : int
Réponse attendue : il manque une relation de persistance entre le gestionnaire et l'objet c. Comme c est recréé à chaque clic, le total repart à 0 — les données ne survivent pas entre deux clics. Il faudrait déclarer c au niveau de la classe qui contient le bouton, pas dans le gestionnaire.
5

Repérer les données (entrées / état / sorties)

🎯 Objectif : comprendre où entrent les données, où elles sont stockées, où elles sortent. Cela permet de voir si le code est pur (sans état) ou stateful.

7

Évaluer la cohérence globale

🎯 Objectif : porter un jugement argumenté. Pas « c'est bien » ou « c'est nul », mais « telle partie est cohérente parce que…, telle autre pose problème parce que… ».

Utilise les 7 questions de la grille D2 :

  1. Cohérence de la structure : chaque entité a-t-elle un rôle unique ?
  2. Encapsulation : les attributs sont-ils privés ?
  3. Découplage : le gestionnaire délègue-t-il ou fait-il tout ?
  4. Duplication : y a-t-il du code recopié ?
  5. Testabilité : peut-on tester chaque méthode séparément ?
  6. Lisibilité : les noms sont-ils clairs ?
  7. Évolutivité : ajouter une fonctionnalité nécessite-t-il beaucoup de modifs ?
