Introduction

Un programme peut être structuré de plusieurs manières différentes pour résoudre le même problème. Ces manières de structurer s'appellent des paradigmes de programmation. Chacun a ses forces, ses limites et ses cas d'usage.

Le critère P3 du BTEC te demande de discuter ce que sont les paradigmes procédural, orienté-objet et événementiel, leurs caractéristiques et les relations entre eux. Le critère M2 te demande de les comparer dans un code source donné. Enfin D2 te demande d'évaluer de façon critique un code source qui implémente les trois, en termes de structure et de caractéristiques.

Qu'est-ce qu'un paradigme ?

Un paradigme est un modèle de pensée : une façon de concevoir, d'organiser et d'écrire un programme. Changer de paradigme, ce n'est pas changer de langage — c'est changer la manière dont on décompose un problème et dont on structure le code qui le résout.

Analogie : imagine que tu doives construire une maison. Tu peux la décrire comme une liste de tâches séquentielles (creuser, couler les fondations, monter les murs…), c'est l'approche procédurale. Tu peux aussi la décrire comme un assemblage d'éléments autonomes (portes, fenêtres, murs) qui interagissent, c'est l'approche orientée-objet. Enfin tu peux la décrire comme un système qui réagit en permanence à des stimuli (on sonne → on ouvre ; il pleut → on ferme les fenêtres), c'est l'approche événementielle.

Classification des paradigmes

Les paradigmes de programmation se classent en deux grandes familles : impérative et déclarative[reference:0].

FamillePrincipeParadigmes associés
Impérative On décrit comment faire : une suite d'instructions qui modifient l'état du programme. Procédural, orienté-objet, structuré[reference:1]
Déclarative On décrit quoi faire : le résultat souhaité, sans préciser les étapes. Fonctionnel, logique, requêtes SQL[reference:2]

Le paradigme procédural et le paradigme orienté-objet appartiennent tous deux à la famille impérative. Le paradigme événementiel est une variante qui s'appuie sur l'impératif mais dont le flux est piloté par les événements.

Paradigme 1
Le procédural

Dans le paradigme procédural, le programme est vu comme une suite d'instructions qui s'exécutent les unes après les autres, regroupées en fonctions (ou procédures). La logique est top-down : on décompose le problème principal en sous-problèmes, puis chaque sous-problème en fonctions[reference:3].

Caractéristiques principales

  • Séquence : les instructions s'exécutent dans l'ordre où elles sont écrites[reference:4].
  • Fonctions / procédures : chaque bloc de code a un nom et peut être appelé plusieurs fois[reference:5].
  • Structures de contrôle : if / else, while, for, switch[reference:6].
  • Variables globales et locales : les fonctions échangent des données via des paramètres et des retours[reference:7].
  • Décomposition fonctionnelle : le code est organisé par ce qu'il fait, pas par ce qu'il manipule.
  • Pas d'encapsulation : il n'y a pas de mécanisme pour cacher les données (tout est public)[reference:8].
  • Appel de procédures statique : les procédures ne sont pas associées à des objets[reference:9].

Exemple — calcul de moyenne

// Deux fonctions : une pour saisir, une pour calculer
int[] saisirNotes(int n) {
    int[] notes = new int[n];
    for (int i = 0; i < n; i++) {
        notes[i] = saisir();
    }
    return notes;
}

double calculerMoyenne(int[] notes) {
    int somme = 0;
    for (int note : notes) {
        somme += note;         // cumul
    }
    return (double) somme / notes.length;
}

// Programme principal : enchaînement des appels
int[] notes = saisirNotes(5);
afficher(calculerMoyenne(notes));

✅ Avantages

  • Simple, direct, rapide à écrire pour de petits programmes[reference:10].
  • Très efficace pour les calculs numériques ou les systèmes avec peu de structures de données[reference:11].
  • Consomme très peu de mémoire[reference:12].
  • Facile à tracer (flux linéaire).

❌ Limites

  • Difficile à maintenir quand le programme grossit[reference:13].
  • Pas d'encapsulation : les données sont exposées[reference:14].
  • Réutilisation limitée : tendance au copier/coller[reference:15].
  • Pas adapté aux applications complexes avec beaucoup de données[reference:16].

Paradigme 2
L'orienté-objet (POO)

Dans le paradigme orienté-objet, le programme est vu comme un ensemble d'objets autonomes qui collaborent. Chaque objet est la représentation d'une entité du monde réel : un Membre, une Activité, une Inscription… Un objet possède des données (attributs) et des comportements (méthodes).

Contrairement au procédural qui sépare les procédures et les données, la POO les rassemble dans une même entité[reference:17].

Les 4 piliers de la POO

Encapsulation

Les données internes d'un objet sont cachées derrière une interface publique. On expose seulement ce qui doit l'être (attributs privés, méthodes publiques).

Héritage

Une classe peut hériter des attributs et méthodes d'une autre. MembrePremium extends Membre hérite de tout "Membre" et ajoute ses propres particularités.

Polymorphisme

Une même méthode peut avoir plusieurs comportements selon la classe réelle de l'objet. calculerCotisation() ne fait pas la même chose pour Membre et MembrePremium.

Abstraction

On ne montre que l'essentiel. La classe Membre expose inscrire() sans révéler comment ça marche en interne.

Exemple — modélisation d'un Membre

public class Membre {
    private String nom;             // encapsulé
    private String email;
    private int cotisation;

    public Membre(String nom, String email) {
        this.nom = nom;
        this.email = email;
    }

    public void inscrire(Activite a) {
        // logique interne, cachée à l'extérieur
    }

    public int calculerCotisation() {
        return 50;
    }
}

public class MembrePremium extends Membre {
    public int calculerCotisation() {   // polymorphisme
        return 120;                     // comportement redéfini
    }
}

✅ Avantages

  • Code réutilisable grâce à l'héritage[reference:18].
  • Proche du monde réel : modélisation par objets[reference:19].
  • Beaucoup plus facile à faire évoluer sur un gros projet[reference:20].
  • Meilleure encapsulation et sécurité des données[reference:21].

❌ Limites

  • Plus abstrait, courbe d'apprentissage plus longue.
  • Surdimensionné pour de petits scripts.
  • Lecture des algorithmes plus difficile : le code est réparti dans plusieurs objets[reference:22].
  • Overhead mémoire et performance pour de très petits programmes[reference:23].

Paradigme 3
L'événementiel (event-driven)

Dans le paradigme événementiel, le programme ne s'exécute pas de manière linéaire. Il attend des événements (clic de souris, touche clavier, message réseau, minuteur…) et réagit à chacun par une fonction associée, appelée gestionnaire d'événement (event handler) ou callback[reference:24].

Le flux d'exécution est déterminé par les événements, non par l'ordre du code. Le programme « attend » au lieu de « faire »[reference:25].

Caractéristiques principales

  • Boucle d'événements (event loop) : le programme principal attend en boucle qu'un événement se produise[reference:26].
  • Gestionnaires : chaque événement est associé à une fonction qui est appelée automatiquement quand l'événement survient[reference:27].
  • Programmation asynchrone : le flux d'exécution est déterminé par les actions de l'utilisateur, non par l'ordre du code[reference:28].
  • Découplage : l'émetteur de l'événement ne sait rien de la fonction qui va réagir.
  • File d'événements : les événements sont mis en file d'attente et traités dans l'ordre où ils surviennent[reference:29].

Exemple — bouton dans une interface

// Association d'un gestionnaire à un événement
boutonInscrire.addActionListener(new ActionListener() {
    public void actionPerformed(ActionEvent e) {
        membre.inscrire(activite);
        afficher("Inscription enregistrée");
    }
});

Dans cet exemple, rien ne se passe tant que l'utilisateur n'a pas cliqué. Le programme n'exécute pas l'inscription : il réagit à un clic.

✅ Avantages

  • Indispensable pour toute interface graphique, serveur web, application mobile[reference:30].
  • Réactivité et comportement asynchrone naturels[reference:31].
  • Découplage fort entre l'émetteur et le récepteur.

❌ Limites

  • Flux d'exécution difficile à lire (code non linéaire).
  • Débogage plus complexe : le bug dépend de l'ordre des événements.
  • Risque de « callback hell » quand les événements s'enchaînent.

Paradigme complémentaire
L'impératif

Le paradigme impératif est basé sur des étapes ou séries d'instructions et fournit une variation de l'état du programme à chaque étape[reference:32]. Il fonctionne en spécifiant la séquence de commandes qui sont exécutées de manière séquentielle et modifient l'état du programme jusqu'à obtenir le résultat final[reference:33].

Le procédural, le structuré et la POO sont tous des sous-domaines du paradigme impératif[reference:34].

CaractéristiqueDescription
Flux de contrôleStructures de contrôle, affectation de variables, entrées/sorties[reference:35]
Boucles conditionnellesfor, while, do-while[reference:36]
Variation d'étatL'état du programme est manipulé à chaque appel de commande[reference:37]
DécompositionDécoupe le programme en petites tâches et fonctions[reference:38]

Langages impératifs typiques : Java, C, C++, C#, Ruby, Matlab, Python, R[reference:39].

Paradigme complémentaire
Le fonctionnel

Le paradigme fonctionnel est basé sur le lambda-calcul d'Alonzo Church, un cadre théorique pour étudier la computation par les fonctions[reference:40]. Contrairement à l'impératif, il ne modifie pas d'état : il compose des fonctions pures.

ConceptDescription
Fonctions puresToujours le même résultat pour les mêmes arguments, sans effet de bord[reference:41]
RécursionPas de boucles for/while : l'itération se fait par récursion[reference:42]
Transparence référentielleUne variable peut être remplacée par sa valeur sans changer le programme[reference:43]
Fonctions de première classeLes fonctions peuvent être passées en paramètre ou retournées[reference:44]
ImmutabilitéOn ne modifie pas une variable après initialisation[reference:45]

Langages fonctionnels typiques : Haskell, JavaScript, Python, Scala, Erlang, Lisp, ML, Clojure, OCaml[reference:46].

Différence clé impératif vs fonctionnel : en impératif on dit comment faire (étape par étape) ; en fonctionnel on dit quoi faire (par composition de fonctions)[reference:47].

Relations entre les trois paradigmes

Ces trois paradigmes ne s'excluent pas : ils se complètent. Dans une même application, on les retrouve souvent tous les trois, chacun au bon endroit.

RelationExplication
OOP ⊃ procéduralLe corps d'une méthode d'objet est écrit de façon procédurale : des instructions qui s'enchaînent. La POO ajoute une couche d'organisation au-dessus du procédural[reference:48].
Événementiel ↔ OOPLes gestionnaires d'événements sont très souvent des méthodes d'objets. Le paradigme événementiel s'appuie naturellement sur la POO.
Événementiel ↔ procéduralOn peut aussi associer un événement à une fonction libre (un callback). L'événementiel est donc compatible avec les deux autres.
ComplémentaritéUne application de bureau typique = une classe Fenetre (POO) + des événements de boutons (événementiel) + des méthodes procédurales de calcul (procédural).

Applications hybrides — le cas le plus courant

Une application réelle implémente presque toujours les trois paradigmes en même temps. Exemple typique : une application de gestion de club sportif en Java.

// 1. POO : la classe Membre encapsule les données
public class Membre {
    private String nom;
    private int age;

    // 2. Procédural : la méthode contient une suite d'instructions
    public int calculerCategorie() {
        int cat;
        if (age < 18) {
            cat = 1;
        } else if (age < 60) {
            cat = 2;
        } else {
            cat = 3;
        }
        return cat;
    }
}

// 3. Événementiel : on réagit au clic d'un bouton
boutonAjouter.addActionListener(e -> {
    Membre m = new Membre(nomSaisi, ageSaisi);
    listeMembres.add(m);
    afficher(m.calculerCategorie());
});

Ce code est procédural dans calculerCategorie(), orienté-objet dans Membre, et événementiel dans le gestionnaire du bouton. C'est cette combinaison qui rend une application réelle lisible, maintenable et réactive à la fois.

Évaluer un code source (D2)

Pour satisfaire le critère D2, tu dois évaluer de façon critique un code source qui implémente les trois paradigmes. Cela signifie aller au-delà de la simple description : il faut juger.

Grille d'évaluation critique — questions à te poser

  1. Cohérence de la structure : les responsabilités sont-elles bien réparties ? Chaque classe a-t-elle un rôle unique (principe de responsabilité unique) ?
  2. Encapsulation : les attributs sont-ils bien privés ? Y a-t-il des getters/setters inutiles qui cassent l'encapsulation ?
  3. Découplage événementiel : les gestionnaires d'événements sont-ils courts et délèguent-ils le travail à des méthodes métier, ou font-ils tout eux-mêmes ?
  4. Duplication : y a-t-il du code recopié (violation du principe DRY) ?
  5. Testabilité : peut-on tester chaque classe et chaque méthode indépendamment ?
  6. Lisibilité : un autre développeur comprendrait-il le rôle de chaque classe sans lire son implémentation ?
  7. Évolutivité : ajouter un nouveau type de membre nécessiterait-il de modifier 10 fichiers ou 1 seul ?
Astuce D2 : pour « évaluer de façon critique », formule toujours un jugement argumenté suivi d'une recommandation. Exemple : « Le code est bien orienté-objet, mais le gestionnaire du bouton contient toute la logique métier : cela rend le code difficile à tester et viole le principe de responsabilité unique. Il faudrait extraire cette logique dans une méthode dédiée de la classe ControleurInscription. »
